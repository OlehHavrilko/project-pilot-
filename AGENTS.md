# Инструкция для агента-разработчика проекта «Пилот»

Ты строишь проект «Пилот»: агента, который сам управляет компьютером под Windows, накапливает
библиотеку навыков и записывает видео с живой озвучкой. Полное ТЗ лежит в `PROJECT_PILOT.md`.
**Прочитай его целиком перед началом любой работы.** Этот файл описывает, *как* работать над проектом.

Общайся с пользователем по-русски. Код, имена и комментарии в коде пиши по-английски.

---

## 1. Как работать

### 1.1. Строго по этапам
- Работай по этапам из раздела 8 ТЗ, по порядку. Не начинай следующий этап, пока текущий не прошёл
  свой критерий «Готово, когда».
- Перед началом этапа коротко напиши план: шаги и как будет проверяться каждый.
- После этапа отчитайся: что сделано, как проверено (команда и её вывод), что осталось.
- Текущий статус веди в `PROGRESS.md`: этап, что готово, известные проблемы, следующий шаг.
  Обновляй его в конце каждой сессии, чтобы следующая сессия могла продолжить с того же места.

### 1.2. Проверяемая цель
- «Готово» значит «проверено запуском», а не «код написан».
- Каждый критерий этапа превращай в скрипт или тест в `tests/` или `scripts/verify_stageN.py`,
  который можно перезапустить.
- Если проверить нельзя (например, нужен человек у микрофона), прямо так и скажи и опиши ручную проверку.

### 1.3. Простота
- Делай минимум, который закрывает текущий этап. Никаких абстракций «на будущее».
- Никаких фреймворков агентов (LangChain и подобных) без явного согласия пользователя: цикл агента — это
  обычный Python-код, его должно быть легко читать.
- Не обрабатывай ошибки, которые не могут случиться. Обрабатывай те, которые реально бывают:
  окно не найдено, таймаут, сеть, протухшая сессия.
- Если решение вышло на 300 строк, а можно уложиться в 80 — перепиши.

### 1.4. Хирургические правки
- Меняй только то, что нужно для задачи. Соседний код, форматирование и конфиги не трогай.
- Заметил постороннюю проблему — запиши её в `PROGRESS.md` в «Известные проблемы», но не чини без запроса.

### 1.5. Неясности
- Если в задаче важная неоднозначность, назови её и спроси. Если вопрос мелкий, прими допущение и явно
  напиши, какое и почему.
- Не выдумывай API библиотек. Сверяйся с документацией (через доступные инструменты документации)
  или с исходниками установленного пакета.

## 2. Окружение пользователя

### 2.0. Цель — Windows, разработка — в WSL
- **Готовый «Пилот» работает на Windows 11** (мозг и мост на Windows-Python 3.12, см. п. 2.8 ТЗ).
- **Ты (агент-разработчик) работаешь в WSL**, потому что это закрытая песочница: все рабочие, временные
  и черновые файлы остаются внутри `~/pilot` и не разбрасываются по Windows.
- Отсюда два жёстких правила:
  1. **Не пиши файлы вне `~/pilot`.** В Windows можно писать только туда, куда разворачивают скрипты
     (`%LOCALAPPDATA%\pilot-bridge\`, позже `%LOCALAPPDATA%\pilot\`) и куда идут тестовые записи
     (`D:\Video\recordly\pilot-tests\`). Временные файлы — в `~/pilot/runs/` или `/tmp`, не в `/mnt/*`.
  2. **Код мозга — кроссплатформенный.** Он должен без правок запускаться и в WSL, и на Windows:
     - пути только через `pathlib` и `config.yaml` (профили `dev` и `win`), никаких захардкоженных `/mnt/...`,
       `/home/...` или `C:\...` в коде;
     - внешние программы (ffmpeg, OBS, Python моста) — по путям из конфига;
     - без Linux-only зависимостей и вызовов (`fcntl`, `os.fork`, сигналы POSIX, shell-конструкции bash);
     - проверка: unit-тесты мозга проходят и на Windows-Python (с этапа 11 — обязательно).
- WSL-специфичные вещи (монтирование дисков, `wslpath`, `powershell.exe` из WSL, mirrored networking)
  допустимы **только в скриптах разработки** (`scripts/`), не в коде мозга.

### 2.1. Работа внутри WSL
- Репозиторий лежит в файловой системе Linux: `~/pilot`. **Не размещай его на `/mnt/c` или `/mnt/d`**:
  файловые операции там в разы медленнее.
- Python в WSL: системный 3.12, проект в `~/pilot/.venv`.
- Системные пакеты ставь через `apt` (с `sudo`, предупредив пользователя). В частности, полный
  `ffmpeg` ставится сюда: `sudo apt install ffmpeg`.
- Диски Windows доступны как `/mnt/c`, `/mnt/d`. Windows-программы запускаются из WSL напрямую
  (`/mnt/c/Program\ Files/obs-studio/bin/64bit/obs64.exe`, `powershell.exe`, `cmd.exe /c ...`).
- Пути переводятся утилитой `wslpath`: `wslpath -w ~/pilot` → путь для Windows,
  `wslpath -u 'D:\Video'` → путь для Linux.

### 2.2. Граница мозга и моста (главное архитектурное правило)
Граница остаётся и в рабочем режиме: тогда мозг тоже на Windows и ходит к мосту на `127.0.0.1`.
Ниже описан режим разработки.

Из WSL **нельзя** напрямую: читать дерево UI Automation, ловить глобальные горячие клавиши Windows,
выводить звук на конкретное Windows-устройство (VB-Cable), снимать скриншоты рабочего стола Windows.

Всё это делает **Windows-мост** (`win_bridge/`, раздел 3.1 ТЗ): отдельный процесс на **Windows-Python 3.12**
со своим venv на Windows-стороне. Правила:
- В мосту нет логики, моделей и ключей API. Только наблюдение, действия, скриншоты, звук, стоп-клавиша.
- Всё, что можно сделать из WSL, делается из WSL: OBS через websocket, Playwright по CDP, файлы
  через `/mnt/*`.
- Мост слушает только `127.0.0.1:8765`, каждый запрос проверяет токен `PILOT_BRIDGE_TOKEN`.
- Развёртывание и запуск моста — скрипт `scripts/deploy_bridge.ps1`. Из WSL он вызывается через
  `powershell.exe -File "$(wslpath -w scripts/deploy_bridge.ps1)"`.
- Мост тестируется отдельно (`win_bridge/tests/`, запуск на Windows-Python), а связка — интеграционными
  тестами из WSL.

### 2.3. Сеть (только разработка)
- Нужен режим **mirrored networking**. Его включает пользователь: файл `%UserProfile%\.wslconfig`
  с секцией `[wsl2]` и строкой `networkingMode=mirrored`, затем `wsl --shutdown`.
  Это настройка Windows — не меняй её сам, а попроси пользователя.
- Проверка: из WSL отвечает `curl http://localhost:8765/health` (мост) и открыт порт 4455 (obs-websocket).
- Если mirrored-режим недоступен, адрес Windows берётся из `ip route show default` (шлюз), а мост
  слушает этот адрес. Это запасной вариант, отметь его в `PROGRESS.md`.

### 2.4. Windows-сторона
- **ОС:** Windows 11 Pro. Оболочка: PowerShell. Есть Git Bash.
- **Python на Windows:** установлены 3.12 и 3.14. Мост работает на **3.12**.
- **OBS Studio 33.0.0:** `C:\Program Files\obs-studio\bin\64bit\obs64.exe`.
  - Профиль и коллекция сцен называются «Безымянный».
  - Конфиги: `%APPDATA%\obs-studio\basic\profiles\Безымянный\basic.ini`,
    `%APPDATA%\obs-studio\basic\scenes\Безымянный.json`, `%APPDATA%\obs-studio\user.ini`.
  - Уже настроено: «Звук раб. стола» идёт на дорожку 1, «Микро» на дорожку 2, запись в MKV с дорожками 1+2.
    Опция «Скрыть OBS от захвата экрана» выключена.
  - Записи сохраняются в `D:\Video\recordly` (из WSL: `/mnt/d/Video/recordly`).
  - obs-websocket встроен в OBS, но его нужно включить: Сервис → Настройки WebSocket-сервера.
    Пароль задаёт пользователь.
- **ffmpeg/ffprobe** на Windows не в PATH (есть только урезанная копия внутри Remotion). При разработке
  проверка записей идёт в WSL полным ffmpeg из apt. Для рабочего режима на Windows нужен полный ffmpeg
  (`winget install Gyan.FFmpeg`, ставит пользователь на этапе 11), путь — в профиле `win` конфига.
- **Видеокарта AMD.** Локальные модели зрения в WSL на AMD работают только при поддержке ROCm. Если её
  нет — CPU или вынос распознавания в мост через ONNX Runtime + DirectML. Решение и причину запиши
  в `PROGRESS.md` на этапе 9.
- **Remotion-проект:** `D:\Projects\codex\remotion`. Это отдельный проект, не трогать.
- **Аудиоустройства:** несколько выходов (High Definition Audio, AMD HDMI на мониторах, Steam Streaming).
  VB-Cable ещё не установлен (нужен на этапе 1). Установку делает пользователь: это системный драйвер.

### 2.5. Ключи и секреты
Только через переменные окружения, никогда в коде, в конфигах в git и в чате:

| Переменная | Где | Для чего |
|------------|-----|----------|
| `DEEPSEEK_API_KEY` | WSL | Все модели агента: исполнитель, планировщик, компилятор |
| `ELEVENLABS_API_KEY` | WSL | Голос |
| `ELEVENLABS_VOICE_ID` | WSL | Голос по умолчанию |
| `OBS_WS_PASSWORD` | WSL | obs-websocket |
| `PILOT_BRIDGE_TOKEN` | WSL **и** Windows | Подпись запросов к мосту (одинаковое значение) |

`.env` в WSL используется только локально, он лежит в `.gitignore`. В репозитории — `.env.example`
без значений. На Windows мост читает только `PILOT_BRIDGE_TOKEN` из пользовательских переменных среды.
Если ключа нет, остановись и попроси пользователя добавить его самостоятельно. Не проси вставить ключ в чат.

## 3. Правила безопасности при разработке и тестах

Агент «Пилот» управляет реальным компьютером пользователя. Пока ты его строишь и тестируешь:

1. **Стоп-клавиша первой.** Её ловит Windows-мост (этап 0). Глобальная клавиша аварийной остановки
   (по умолчанию `Ctrl+Alt+Q`) должна работать до первого запуска цикла агента (этап 3) и обрывать
   действия, даже если процесс в WSL завис. Проверь её отдельно.
2. **Белый список программ.** Агент действует только в программах из `config.yaml → safety.allowed_apps`.
   На время разработки: OBS Studio, Блокнот, Проводник и тестовый браузер Playwright.
3. **Опасные действия** (удаление, отправка сообщений, публикация, оплата, изменение системных настроек
   Windows) агент выполняет только после подтверждения пользователя. Это проверяется в коде, а не промптом.
4. **Тесты на сайтах** — только на тестовых страницах или локальных стендах, не на реальных аккаунтах
   пользователя без его прямого разрешения.
5. **Конфиги чужих программ** (OBS и т. д.) меняй только при закрытой программе и только после бэкапа
   в `backups/<дата>/`. Иначе программа перезапишет изменения при выходе.
6. **Лимиты** в каждом запуске агента: максимум шагов, времени и запросов к моделям. Значения по умолчанию
   задаются в `config.yaml`.
7. **Ничего не удаляй** в файлах пользователя вне репозитория. Тестовые записи OBS складывай в отдельную
   подпапку `D:\Video\recordly\pilot-tests\`.

## 4. Технические соглашения

### 4.1. Структура
Следуй структуре из раздела 7 ТЗ. Новые папки верхнего уровня добавляй только при реальной необходимости
и отмечай это в `PROGRESS.md`.

### 4.2. Код
- Python 3.12, аннотации типов, `ruff` для линтинга и форматирования.
- Зависимости — в `pyproject.toml`. Новую зависимость добавляй, только если без неё никак, и пиши, зачем она.
- Одна задача — один модуль. Модули по 100–300 строк — нормально, на 1000 — пора делить.
- Логи через стандартный `logging`. Журнал сессии агента пишется отдельно в JSONL (`runs/<время>/session.jsonl`).

### 4.3. Модели
- Все модели агента — **только DeepSeek**, flash-модель. Anthropic и другие провайдеры в рантайме
  не используются.
- Все вызовы идут только через `models/adapter.py`. Роль → модель и режим рассуждения задаются
  в `config.yaml`:
  ```yaml
  models:
    executor:  {model: <deepseek-flash>, reasoning: off}
    planner:   {model: <deepseek-flash>, reasoning: high}
    compiler:  {model: <deepseek-flash>, reasoning: high}
  planner_images: false   # true, если выбранная модель DeepSeek принимает изображения
  ```
  `<deepseek-flash>` и способ включить глубокое рассуждение возьми из актуальной документации
  DeepSeek API. Не угадывай имя модели: проверь запросом к `/models` и одним пробным вызовом.
- Планировщик по умолчанию получает скриншот текстом (разбор OmniParser), а не картинкой.
- Каждый вызов логирует роль, модель, число токенов и время ответа.
- Ответы исполнителя и компилятора — строго JSON по схеме. Невалидный JSON повторяется один раз
  с сообщением об ошибке, потом передаётся планировщику.

### 4.4. Навыки
- Формат навыка — раздел 4.4 ТЗ: `skill.py`, `manifest.json`, `check.py`, `log.jsonl`.
- Навык без рабочего `check.py` в библиотеку не попадает.
- У навыков, которые используются в режиме записи, две реализации: `run_fast()` (API) и `run_visible()`
  (через видимый интерфейс).
- Навыки, сгенерированные компилятором, помечаются `"generated": true` и проходят те же проверки, что и ручные.

### 4.5. Действия и наблюдение
- Единый набор действий из раздела 4.1 ТЗ. Каждый вход (api, cli_config, cdp, uia, vision) реализует
  один и тот же интерфейс.
- Наблюдение всегда отдаётся в текстовом формате из раздела 2.3 ТЗ, с номерами элементов.
  Номера стабильны в пределах одного шага.
- Координаты пикселей используются только во входе `vision`. Все остальные входы адресуют элементы
  по идентификатору.

### 4.6. Голос и запись
- Голос агента выводится на устройство VB-Cable. В OBS это отдельный источник на дорожке 2, микрофон
  пользователя переносится на дорожку 3 (см. раздел 4.8 ТЗ). Перенастройку OBS делай через
  obs-websocket, а не правкой файлов, когда это возможно.
- После каждой тестовой записи автоматически проверяй файл: число дорожек и наличие звука в каждой
  (`ffprobe` + `silencedetect`).

## 5. Тесты

- `tests/unit/` — чистая логика без внешних систем (разбор ответов моделей, слияние наблюдений,
  формат навыков). Запускаются всегда.
- `tests/integration/` — с реальными OBS, окнами и API. Помечены `@pytest.mark.integration`, запускаются
  явно. Перед запуском проверяют, что нужная программа открыта, а ключи заданы, иначе `skip` с понятной причиной.
- `scripts/verify_stageN.py` — проверка критерия этапа N. Её вывод прикладывается к отчёту об этапе.
- Ответы моделей в unit-тестах подменяются записанными примерами (`tests/fixtures/`), чтобы не тратить
  запросы.

## 6. Git

- Работа идёт в ветках `stage-N-<кратко>`. Коммиты небольшие и осмысленные, сообщения по-английски.
- Не коммить `.env`, `runs/`, `backups/`, видео и аудио файлы, кеш голоса.
- Коммить и пушить — только когда пользователь попросит или когда это оговорено в начале сессии.

## 7. Отчёт пользователю

В конце каждой сессии кратко и по-русски:
1. Что сделано.
2. Как проверено: команда и результат. Если что-то не проверено — прямо сказать.
3. Что требует действий пользователя (установить VB-Cable, включить websocket, добавить ключ).
4. Следующий шаг.

Пользователь пишет коротко и разговорно. Отвечай по делу, без воды и без лишних оговорок.
